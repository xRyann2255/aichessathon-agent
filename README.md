# AI Chessathon agent

The chess engine I entered in the [AI Chessathon 2026](https://aichessathon.com), the UK's first chess hackathon, as a one-person team. It finished 2nd of 465 teams in the online qualifier, held the highest peak rating of the qualifier, and placed 5th in the London final on 12 September 2026. This repository is the build as uploaded (v87): the same 115 files, byte for byte, and nothing else.

## The contract it ran under

The platform imports `agent.py` and calls `get_move(fen, time_left_ms)`, which returns a move in UCI (`e2e4`, `e7e8q`). Each game is one fresh process on one core of an AMD EPYC 9V74 with 2 GB of RAM, no GPU and no network, suspended while the opponent thinks. The clock is 120 s a side plus 0.5 s a move, and the import has to finish inside a 90 s budget before the clock starts. The zip is capped at 50,000,000 bytes and may hold Python source and data only. No third-party engine may be shipped in any form, and a network is allowed only if the team trained it. Openings were curated positions chosen by the organisers, not always the standard start. Games that reached 600 plies were drawn.

The installed packages were Python 3.12 with numpy 2.5.2, numba 0.67.0 and python-chess 1.11.2. The engine uses those three and nothing else.

## What is in the zip

| File | Role |
|---|---|
| `agent.py` | The entrypoint: turns the FEN into the kernel's position, runs the deepening loop, manages the clock, tracks repetitions across the game, checks every move before returning it |
| `kernel.py` | The board as numba kernels over preallocated arrays: bitboards, pseudo-legal move generation, make and unmake, Zobrist hashing, attack tests |
| `search.py` | Fail-soft alpha-beta with principal variation search, null moves, late move reductions, static exchange pruning, killer and history tables, a one-word-per-entry transposition table, quiescence |
| `nnue.py` | The network's integer forward pass inside the kernel, with hand-written AVX2 and AVX-512 intrinsics for the packed multiply-add |
| `evaluation.py` | Tapered piece-square tables, used where the net is missing or cannot help |
| `bitboards.py` | The attack tables the kernel reads |
| `book.py` | Opening book lookup before the search |
| `tablebase.py` | Syzygy and KPK bitbase probes at the root and in the search |
| `diag.py` | The diagnostic lines the platform's per-game log kept |
| `weights/*.safetensors` | The network, trained by me. HalfKA features with 4 king buckets, a 256-wide int16 accumulator per side, a pairwise product into two 32-wide layers and one output. 1.45 MB |
| `weights/*.check.json` | Positions with the net's expected scores, checked at import so a wrong forward pass fails before the first game |
| `weights/book.pack` | The opening book: 923,787 positions at ten bytes each, the polyglot key and move word with the two fields the lookup never reads left out. 9.2 MB |
| `weights/kpk.bin` | A king-and-pawn-against-king bitbase generated by retrograde analysis and checked against Syzygy on all 165,676 legal positions. 24 KB |
| `weights/syzygy/` | Every 3-man and 4-man Syzygy table plus a subset of the 5-man tables, chosen by measuring which endings engines actually misplay. 65 tables, 30 of them 5-man, 38 MB |

The book and the tablebases are data the rules permitted: a shipped table may answer the opening (move 20 or lower) or the endgame (at most seven pieces). The book answers nothing past move 20 and the tables nothing above five pieces. Every other move comes from the search.

## How it plays

Everything between parsing the FEN and printing the move runs in numba, compiled at import so nothing is compiled on the clock. The import takes about 25 s on the platform's core. The search reached 24 to 28 ply at the tournament clock in rated games.

The net's accumulators are kept per ply and updated incrementally as the search makes moves; nothing is undone, because the parent's pair is untouched when a move is taken back. The head runs at the leaves as integers throughout, with every rescale a shift. numba would not emit the packed byte multiply-add on its own, so it is written as a direct call to the LLVM intrinsic, AVX-512 VNNI where the host has it and AVX2 otherwise, chosen once at import. That read 1.27 times the nodes a second of the plain loop on the same tree.

The time manager was designed from the platform's own game logs rather than from local runs, because the platform's core ran about 1.4 times slower than the development machine and rated games were ending with clock unspent. The opening book was built to reach as deep as the zip's room allowed: a mean exit at move 17 on the organisers' published starting positions. A mate score, a tablebase result and a bitbase result are treated as verdicts, never as estimates, so nothing that averages or learns from evaluations is allowed to read one.

## Running it

```
pip install numpy==2.5.2 numba==0.67.0 chess==1.11.2
python -c "import agent; print(agent.get_move('rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1', 120000))"
```

The import compiles the kernels and takes 20 to 30 s; the first call then answers within the time the clock allows. The process keeps its state between calls, so one process plays one game and a new game needs a new process. Expect about 500 MB of memory.

## What is not here

The training pipeline, the book builder, the match instrument, the notes and the measurements that decided each change stay in the private development repository. This one holds the engine as it played.
